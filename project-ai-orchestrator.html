AI-Driven Infrastructure Orchestrator

An AI-powered software development orchestrator designed to make AI an active participant in the engineering workflow. It receives development tasks, selects the appropriate engineering persona based on the programming language, and builds an understanding of the existing codebase by gathering relevant context through a dedicated repository-reading tool. Using this context, it generates code aligned with the repository's structure and requirements, then creates a GitHub Pull Request for human review.

01. Design Goal

The goal was to build a pluggable AI development orchestrator that can take on different engineering tasks while operating within clearly defined boundaries. Each programming language has its own engineering persona and repository scope, controlling where the AI can access and generate code. Repository mapping determines which directories and files are visible to the model, with configurable exclusions preventing designated content from entering its context or being accessed through file-reading requests. Retrieved file content is also inspected and sensitive information is redacted before being exposed to the model. This creates an extensible framework where AI can understand and work within an existing codebase while maintaining controlled access, language-specific boundaries, and human oversight of generated changes.

02. Configuration-Driven Language Routing and Persona Selection

Jira labels identify the programming or configuration language associated with each development task. The orchestrator matches the label against registered language profiles, which define the engineering persona, repository scope, and language-specific output handling. This keeps language-specific instructions and execution parameters separate from the core orchestration logic.

Routing follows an explicit validation model. If a ticket has no matching registered language label, the orchestrator stops execution and reports the issue rather than guessing the intended language or selecting an arbitrary persona.

Impact: Adding support for another language requires defining its engineering persona and registering the corresponding profile, without changing the core orchestration logic. This makes the system extensible while keeping language selection predictable and controlled.

03. Orchestrator as Control Layer

The orchestrator serves as the central control layer between Jira, the LLM, and GitHub. It receives incoming development tasks, manages the execution sequence, coordinates interactions between these components, and controls how information and generated changes move through the workflow.

Impact: This creates a clear separation of concerns. Jira defines intent, the LLM handles generation, and GitHub manages version control and code review. The orchestrator coordinates the process and enforces the workflow logic, simplifying maintenance and allowing each component to evolve independently.

04. Prompt as Code

Each engineering persona is defined in its own version-controlled Markdown file rather than being embedded in the application logic. These files are not generic prompts, they establish the role the model is expected to assume, along with its technical responsibilities, coding standards, and task-specific instructions.

When a Jira label matches a registered language profile, the orchestrator loads the corresponding persona prompt to guide code generation. Alongside it, a shared standard.md file is always loaded to provide common engineering conventions that apply across all personas, such as naming conventions and consistency standards.

Impact: Treating prompts as code makes AI behaviour visible, reviewable, and maintainable. Prompt changes can go through pull requests and version control, just like application code or infrastructure configuration. Separating shared standards from language-specific instructions also makes it easier to maintain consistent engineering practices across different personas, while allowing each persona to evolve independently without changing the core orchestration logic.

05. Structured Output Enforcement

The orchestrator defines an explicit output contract for the LLM through its persona instructions. Each response is expected to follow a consistent structure containing a file path (PATH:) and the generated code (CODE:), with no additional explanatory text. This gives the orchestrator a predictable format to work with when processing generated changes.

The response is then normalized before further processing. Regex-based handling removes Markdown code fences and standardizes field labels, accommodating common formatting variations in LLM responses.

Impact: Defining a consistent output contract reduces ambiguity and makes generated responses easier for the orchestrator to process. Rather than relying on unrestricted natural-language responses, downstream processing can work with clearly identified fields. This improves consistency and predictability across different engineering personas.

06. Context Injection

The orchestrator provides the LLM with a structured map of the repository, giving it visibility into the available files and directory structure within its permitted scope. Rather than automatically loading project files into the prompt, the model can use this map to identify relevant files and request their contents through a dedicated repository-reading tool. The orchestrator validates each request against the allowed repository scope and applies sensitive-data redaction before returning file contents.

Impact: This allows the model to build an understanding of the existing codebase before generating changes, without loading the entire repository into its context. It also keeps repository access controlled, limits unnecessary context, and helps generated code align with the existing project structure.

07. Retry with Error Context

When CI/CD validation fails, the system captures the error output and feeds it back into the LLM as additional context for a correction attempt.

Impact: This introduces an iterative feedback loop that reduces manual debugging. Instead of stopping at failure, the system attempts to correct itself, moving toward a more resilient workflow.

08. Scoped GitHub Bots

I used separate bot identities in GitHub for different domains, such as infrastructure and configuration.

Impact: This enforces least-privilege access and improves security. It also makes ownership of automated changes clearer, which is important in collaborative environments.
