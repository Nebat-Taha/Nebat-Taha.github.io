AI-Driven Infrastructure Orchestrator

An AI-powered software development orchestrator designed to make AI an active participant in the engineering workflow. It receives development tasks, selects the appropriate engineering persona based on the programming language, and builds an understanding of the existing codebase by gathering relevant context through a dedicated repository-reading tool. Using this context, it generates code aligned with the repository's structure and requirements, then creates a GitHub Pull Request for human review.

01. Design Goal

The goal was to build a pluggable AI development orchestrator that can take on different engineering tasks while operating within clearly defined boundaries. Each programming language has its own engineering persona and repository scope, controlling where the AI can access and generate code. Repository mapping determines which directories and files are visible to the model, with configurable exclusions preventing designated content from entering its context or being accessed through file-reading requests. Retrieved file content is also inspected and sensitive information is redacted before being exposed to the model. This creates an extensible framework where AI can understand and work within an existing codebase while maintaining controlled access, language-specific boundaries, and human oversight of generated changes.

02. Configuration-Driven Language Routing and Persona Selection

Jira labels identify the programming or configuration language associated with each development task. The orchestrator matches the label against registered language profiles, which define the engineering persona, repository scope, and language-specific output handling. This keeps language-specific instructions and execution parameters separate from the core orchestration logic.

Routing follows an explicit validation model. If a ticket has no matching registered language label, the orchestrator stops execution and reports the issue rather than guessing the intended language or selecting an arbitrary persona.

Impact: Adding support for another language requires defining its engineering persona and registering the corresponding profile, without changing the core orchestration logic. This makes the system extensible while keeping language selection predictable and controlled.

03. Orchestrator as Control Layer

The orchestrator serves as the central control layer between Jira, the LLM, and GitHub. It receives incoming development tasks, manages the execution sequence, coordinates interactions between these components, and controls how information and generated changes move through the workflow.

Impact: This creates a clear separation of concerns. Jira defines intent, the LLM handles generation, and GitHub manages version control and code review. The orchestrator coordinates the process and enforces the workflow logic, simplifying maintenance and allowing each component to evolve independently.

04. Prompt as Code

Each engineering persona is defined in its own version-controlled Markdown file rather than being embedded in the application logic. These files are not generic prompts, they establish the role the model is expected to assume, along with its technical responsibilities, coding standards, and task-specific instructions.

When a Jira label matches a registered language profile, the orchestrator loads the corresponding persona prompt to guide code generation. Alongside it, a shared standard.md file is always loaded to provide common engineering conventions that apply across all personas, such as naming conventions and consistency standards.

Impact: Treating prompts as code makes AI behaviour visible, reviewable, and maintainable. Prompt changes can go through pull requests and version control, just like application code or infrastructure configuration. Separating shared standards from language-specific instructions also makes it easier to maintain consistent engineering practices across different personas, while allowing each persona to evolve independently without changing the core orchestration logic.

05. Structured Output Enforcement

The orchestrator defines an explicit output contract for the LLM through its persona instructions. Each response is expected to follow a consistent structure containing a file path (PATH:) and the generated code (CODE:), with no additional explanatory text. This gives the orchestrator a predictable format to work with when processing generated changes.

The response is then normalized before further processing. Regex-based handling removes Markdown code fences and standardizes field labels, accommodating common formatting variations in LLM responses.

Impact:strong> Defining a consistent output contract reduces ambiguity and makes generated responses easier for the orchestrator to process. Rather than relying on unrestricted natural-language responses, downstream processing can work with clearly identified fields. This improves consistency and predictability across different engineering personas.

06. Configuration-Driven Language Routing and Persona Selection

The orchestrator provides the LLM with a structured map of the repository, giving it visibility into the available files and directory structure within its permitted scope. Rather than automatically loading project files into the prompt, the model can use this map to identify relevant files and request their contents through a dedicated repository-reading tool. The orchestrator validates each request against the allowed repository scope and applies sensitive-data redaction before returning file contents.

Impact: This allows the model to build an understanding of the existing codebase before generating changes, without loading the entire repository into its context. It also keeps repository access controlled, limits unnecessary context, and helps generated code align with the existing project structure.

07. Security and Guardrails

Webhook Authentication

The Jira webhook endpoint requires a shared secret supplied through a request header. The orchestrator validates this secret using a constant-time comparison before accepting a request for processing. If the secret is missing from the configuration or the request fails authentication, the webhook is rejected.

Repository Access Controls

Repository visibility is configurable, allowing designated files and directories to be excluded from the model's view. These exclusions are applied when generating the repository map, so excluded content is not exposed to the model as part of the available project structure. Language profiles also define the repository scope available to each engineering persona, further restricting which parts of the codebase it can access.

The dedicated file-reading tool independently validates requested paths, rejects absolute paths and path traversal attempts, and rechecks repository exclusions before accessing the filesystem. Generated file paths are also restricted to the selected language's configured scope, and existing files cannot be overwritten.

Execution Limits and Model Guardrails

The orchestration loop uses configurable boundaries to prevent uncontrolled model interactions. The current implementation limits context-gathering to 15 passes, allows up to five distinct file reads, and provides up to three code-generation attempts.

Additional guardrails prevent premature code generation during the repository investigation phase. Repeated requests for invalid file paths trigger an abort and a notification for human review.

Sensitive-Data Protection

File contents are inspected and sensitive information is redacted before being returned to the model. This includes common patterns such as email addresses, IP addresses, AWS account IDs, secret assignments, and configurable organization-specific terms.

A separate outbound security check scans generated code before GitHub submission. If sensitive information is detected, the submission pipeline is stopped rather than allowing the content to proceed.

Impact: These controls establish boundaries around what the model can access, how it interacts with the repository, and what it can submit. By combining request authentication, path validation, execution limits, data redaction, outbound scanning, and language based scope, the orchestrator reduces the risk of unintended access or sensitive-data exposure while keeping the workflow under human oversight through GitHub Pull Requests.

08. Technology Stack

The orchestrator brings together five core technologies and integrations, each serving a distinct role in the system.

Core Application — Python

Python provides the foundation for the orchestrator. It handles the application logic, coordinates the workflow, manages interactions between components, and controls the processing of development tasks.

API Layer — FastAPI and Uvicorn

FastAPI exposes the webhook endpoint that receives Jira events and passes incoming requests into the orchestration process. Uvicorn runs the application as the ASGI server.

LLM Runtime — Ollama and Phi-3

Ollama provides the local runtime for hosting and interacting with the language model. The project currently uses Phi-3 for understanding development tasks, analyzing repository context, and generating code based on the selected engineering persona.

Task Management — Jira REST API and Webhooks

Jira webhooks trigger the orchestration process when a development request is received. The Jira REST API is used to retrieve the associated issue information, including its summary, description, and labels.

Version Control — GitHub API and PyGithub

GitHub provides the repository and code review platform. The orchestrator uses PyGithub to interact with GitHub, create a branch, commit generated changes, and open a Pull Request for human review.

09. End-to-End Workflow

The workflow begins when a development request is submitted through Jira and ends with a GitHub Pull Request ready for human review. The orchestrator coordinates each stage, from task interpretation and repository investigation to code generation and submission.

Workflow Overview

  1. Jira Development Request

    A webhook triggers the orchestrator. Issue details and labels are retrieved for processing.

  2. Language Routing and Persona Selection

    Jira labels are matched to a registered language profile and its corresponding engineering persona.

  3. Repository Discovery and Context Retrieval

    The repository map is provided to the model, which requests relevant file contents through the controlled repository-reading tool.

  4. Code Generation and Output Processing

    The model generates code according to the selected persona and output contract. The response is normalized and processed by the orchestrator.

  5. GitHub Pull Request

    The generated file is committed to a new branch and submitted through a Pull Request for human review.

1. Jira Request Reception

A Jira webhook sends the development request to the FastAPI endpoint. After authenticating the request, the orchestrator retrieves the issue details and extracts the information needed to begin processing, including the task description and language labels.

2. Language Routing and Persona Selection

The orchestrator matches the Jira labels against the registered language profiles. The selected profile determines which engineering persona and repository scope will be used for the task. If no supported language is identified, execution stops rather than proceeding with an arbitrary configuration.

3. Repository Discovery and Context Retrieval

The orchestrator generates a filtered repository map based on the selected profile and configured exclusions. The model uses this map to identify relevant files and requests their contents through the dedicated repository-reading tool. Requested paths are validated, and retrieved content is inspected for sensitive information before being returned to the model.

4. Code Generation and Output Processing

With the relevant repository context available, the model generates code according to the selected persona's instructions and the defined output contract. The orchestrator processes the response, extracts the target file path and code, and applies the applicable output checks before preparing the change for submission.

5. GitHub Pull Request Creation

Once the generated output passes the applicable checks, the orchestrator creates a new branch, commits the generated file, and opens a Pull Request. The change is then available for human review through the existing GitHub workflow.

Human Review: The process concludes with a Pull Request, not an automatic merge. Human review remains the final checkpoint before generated changes can become part of the codebase.

10. Future Enhancements

The current implementation establishes the core orchestration workflow, from receiving a development task to submitting generated code for human review. There are several areas where the architecture can evolve further.

Automated Correction and Retry Loop

Extend the workflow to consume CI/CD feedback from failed validation or test runs. The orchestrator could return relevant error context to the model, allowing it to investigate and propose corrections within defined retry limits before requesting human intervention.

Controlled Updates to Existing Files

The current implementation prevents generated changes from overwriting existing files. A future enhancement could introduce a controlled update mechanism that permits modifications only to files previously created and owned by the orchestrator, while preserving restrictions on unrelated repository files.

Expanded Engineering Personas

Extend the existing language-profile architecture to support additional engineering personas and development workflows. This could allow the same orchestration framework to handle a broader range of engineering tasks while retaining task-specific instructions and repository boundaries.

Expanded Validation and Quality Checks

Introduce more comprehensive validation of generated output, including stricter path and content checks, syntax validation, and automated tests before changes are submitted to GitHub.
